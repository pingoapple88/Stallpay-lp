## 二、附件對目前結論造成的調整

### 2.1 必須保留的既有判定

| 判定 | 是否改變 | 原因 |
|---|---|---|
| T7 不直接退款 | 不變 | 補償只產生 intent，正式退款由核准支付 provider／owner 處理 |
| T7 不修改正式庫存 | 不變 | ERP Core 是正式庫存與財務事實層 |
| unknown 不自動重送 | 不變 | 送出後結果不明必須先查狀態或人工對帳 |
| Generic status 不是天來正式狀態 | 不變 | v2.7、fault code 與實機回應尚未獲 owner 核准 |
| GATE-06 維持 BLOCKED | 不變 | 缺正式 owner、核准文件、Base URL 分類、指定測試機與實機證據 |

### 2.2 新增的關鍵認知

附件顯示目前十二情境偏重「單機、單格、單品與前端可視狀態」，而實際 P0 還包含 **全鏈 scope、多格履約、付款成功後例外、重複回執、錯格／錯品、mapping 缺失與 operation idempotency**。因此下一版測試軟體不應只增加更多故障按鈕，而要建立一個可追溯的 canonical scenario catalog，每個情境都能連回附件 ID、owner、Gate、前置條件、狀態序列與停止規則。[1]

## 三、測試軟體調整方案

### 3.1 vNext 產品目標

將目前分散於「十二情境自助套件」、「舊版八情境卡片」與「CLI generic harness」的能力，整併成單一測試目錄。第一階段不追求模擬全部 329 個情境，而是建立 **32 個 P0 安全情境**：沿用 12 個現有網站情境，再新增 20 個高風險情境。

| 調整項目 | 現況 | vNext 需求 | 驗收方式 |
|---|---|---|---|
| 情境目錄 | 情境分散且命名有重疊 | 單一 canonical catalog；每筆有附件 source ID、類別、owner、mode、Gate | UI 與 JSON／CSV 使用相同 scenario ID |
| 分類導覽 | 十二張卡片平鋪 | 增加 QR／scope、mapping／庫存、設備 operation、故障安全、對帳／補償分類 | 可依分類篩選並執行完整分類套件 |
| 前置條件 | 只有基本設備／場域／SKU | 增加 order ref、operation ref、idempotency key、machine／slot／commodity scope、多格清單、付款狀態 | 缺欄位時 fail-closed，不產生假成功 |
| Expected／Actual | 目前只顯示固定結果 | 同時顯示 expected sequence 與 actual simulated sequence，標示差異 | 任一不一致為 `NEEDS_REVIEW` |
| 多格履約 | 尚無 | 模擬全成功、部分成功、錯格與未 ready | 每格有獨立 receipt 與整單狀態 |
| Idempotency | 有舊版情境但未納入十二情境 | 納入 canonical full suite，區分同 payload replay 與不同 payload conflict | 重播不產生第二 operation |
| 付款後例外 | 只有 compensation intent | 增加已付款無空格、明確失敗、結果 unknown 三種 | unknown 凍結退款與重送；明確失敗只產生 intent |
| Scope 安全 | 未形成可見情境 | company／store／machine／slot／commodity 不一致均可測 | mismatch 必須 `BLOCKED` 並留下 audit intent |
| Mapping | 只查 Machine／Commodity | 新增「mapping 缺失／矛盾」的 synthetic 情境；正式 read-only mapping 仍 Gate | 不猜 `commodity_code`／slot |
| Evidence | session-only JSON／CSV | 保留去敏匯出，新增 source IDs、expected／actual、owner、Gate、audit ref、safety assertions | 不含 Token、sign、完整 query、PII 或 raw upstream body |
| 完成判定 | 單一 `SIMULATOR_VERIFIED` | 分成 `SCENARIO_CATALOG_VERIFIED`、`READ_ONLY_CONNECTIVITY_VERIFIED`、`TEST_DEVICE_VERIFIED` | 前兩者不得自動解除 GATE-06 |
| 語系／裝置 | 五語介面已有基礎 | 新增情境名稱、錯誤與安全文案同步五語；桌機、手機、Kiosk 驗證 | 五語 fallback、keyboard、ARIA live 與 RWD 有證據 |

### 4.3 測試軟體 vNext 驗收條件

| 驗收面向 | 必須通過 |
|---|---|
| 情境完整性 | 32 個 P0 情境均有唯一 ID、附件 source IDs、owner、mode、evidence level 與 Gate |
| 狀態安全 | unknown、送出後斷線、timeout、sensor conflict、部分成功全部禁止自動重送 |
| Idempotency | 同 key 同 payload 回既有 receipt；同 key 不同 payload 必須 blocked |
| 多格 | 每格獨立 receipt；部分成功不可把整單標 completed |
| Scope | company／store／machine／slot／commodity 任一不一致即 blocked |
| 付款後例外 | paid no slot、failed、unknown 均只產生人工／補償 intent，不直接退款 |
| 庫存 | 所有結果只輸出 synthetic inventory／reconciliation intent，不修改 ERP 正式庫存 |
| Evidence | JSON／CSV 包含 expected／actual、UTC、operation ref、audit ref、safety assertions；不含 secret、PII、sign 或 raw response |
| UI | 五語 fallback、桌機／手機／Kiosk、keyboard、focus、ARIA live、loading／empty／error／blocked／manual review |
| 完成訊號 | 模擬、唯讀連通、test-device 三層分離；只有具備實機證據與 Dennis 簽核才可申請 `TEST_DEVICE_VERIFIED` |
